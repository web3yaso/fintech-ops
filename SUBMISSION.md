Ten bullets, grouped by the five questions asked.

## 1 · What problem I chose to solve

- **Problem.** The question underneath this brief is what it actually takes for AI agents to make an ops team more effective — and the data says the answer is not "answer tickets faster," because per-ticket speed was never the bottleneck. Ops handles every ticket as an isolated unit, so the expensive problems — the ones that live *across* tickets — go unseen: in the dataset only ~9 of 100 tickets are genuinely unique work; 53 are ten verbatim-repeat FAQs, 23 belong to two never-declared burst incidents (a 4-day online card-decline outage, 14 tickets under 14 different subject lines; ≥$342k of delayed inbound USD wires, 5 of 9 still unresolved), 11 form a three-week FX-pricing complaint trend from 10 customers, and 4 high-risk items (a likely account takeover, a $4,850 unrecognized charge) hide under subjects like "Quick question." So the problem I chose: give one ops generalist an AI execution layer that reclaims that hidden cross-ticket work — detects it, investigates it, hands it to the teams that own the fixes, and tracks it to confirmed closure — while every consequential decision stays human-owned. Real agent leverage is structural, not conversational.

## 2 · Why I chose it

- **Why this problem.** It's where the numbers break: cross-ticket segments run 23–37h at CSAT 1.5–1.8 versus 5.6h and 3.7 for the FAQ half of the queue — and no amount of faster per-ticket handling fixes a cross-ticket failure. For a lean FINTRAC-registered payments company, undetected incidents, silent churn signals and buried fraud are the costliest categories of operational risk.

## 3 · How my solution works

- **Cross-ticket failure has two speeds, so the tool has two detectors.** A burst detector (≥3 similar tickets in 72h) catches outage-shaped incidents. A trend detector (≥5 customers over ≥14 days at low CSAT) catches slow burns the burst window is structurally blind to — like the FX cluster, where even the densest 72h span holds just 3 of the 11 tickets, so a burst-only view would misread a three-week erosion as one minor blip. A precedence rule (trend beats burst when the theme already spans ≥14 days) prevents double-reporting. That cluster is the demo's proof the tool finds patterns nobody pre-configured — and because the mock helpdesk replays the dataset as a live stream, the demo shows the card-decline incident being *caught in real time*, on the third arriving ticket, not diagnosed after the fact.
- **What I built.** A four-agent AI ops team — Triage, Pattern Commander, Case Worker, Liaison — sized by a simple rule: an agent exists only where LLM judgment is needed; classification is a function call and reporting is a script. They live in a real chat UI (OpenMausBot war room + a separate standup room, alongside three clearly-SIMULATED persona colleagues from eng/product/compliance), and produce *internal work packages*, not just replies — for a missing $118k wire, an investigation checklist, a ready-to-send partner-bank inquiry, and an honest customer update; for the FX trend, a churn-risk escalation with the affected-customer table and verbatim quotes. The org-shape claim: one execution layer under a single human owner — the tool compresses hand-off surfaces (14 subject lines → one incident; queue → engineering in one gated step), not headcount.
- **How it works, mechanically.** Tickets arrive through a `HelpdeskAdapter` seam — a mock helpdesk API that **replays the dataset as a real-time stream** on an accelerated clock (plus a CSV batch fallback) — then flow through one pipeline: LLM enrichment into a pydantic-validated schema (temperature 0, auto-retry, `needs_human` on repeated failure) → deterministic burst + trend clustering → an explainable priority score (severity × log-MRR × age, formula shown in output). Triage labels and internal notes are written back to the helpdesk, and skills consume the pipeline's files without ever re-deriving them.
- **Found patterns don't die in ops — and found is not fixed.** Liaison translates each confirmed finding for the team that owns the fix — engineering bug reports with correlation hypotheses, product briefs with customer quotes and revenue at risk, help-center drafts — filed as tracker issues (mock Jira) and pinged to named owners, but only on the incident manager's go-ahead. Every declared pattern then carries a closure state machine (escalated → acked → fix confirmed → customers notified → closed, with "closed" requiring theme volume back to baseline), so the weekly brief reports **time-to-close beside time-to-declare** — the tool knows the difference between detecting a problem and actually resolving it for the customers who reported it. A git-tracked `knowledge/` folder is the two-way bus between teams.
- **The team learns on four channels, each with the right authority.** Label corrections (ops-role-gated, enforced in code) become overrides + few-shot + eval cases in one step. Behavioral coaching distills into capped, git-audited NOTES.md files. Agents self-learn into per-agent KNOWLEDGE.md — facts only, never rules (the prompt-injection firewall) — via nightly-journal and weekly-digest routines plus learn-on-correction, committing their own knowledge under their own git author. And SKILL.md itself evolves humans-only: agents file frozen old→new proposals, a daily digest reaches the operator in chat, and she approves or rejects with one chat reply — the executing agent can apply only the recorded diff, never shape it.
- **Measured, not vibed.** A 24-ticket hand-labeled eval runs the exact production code path (overrides off, few-shot on, leave-one-out): two staff corrections lifted segment accuracy **75% → 96%** by generalization — and the same run caught a coaching side effect (one fraud correction dragged ops_workflow 88% → 83% on adjacent tickets). Detection on the full dataset: **wires 9/9, FX trend 11/11, declines 14/14, zero false positives** — the 14th decline member was recovered by a human-ratified merge rule sourced from an agent's own journal, the learning loop closing into the deterministic layer. Every number in this document is recomputed from the CSV and the segments sum to 100.

## 4 · Key assumptions I made

- **Key assumptions.** Ticket text is the only system of record available to the tool; monthly revenue is a fair proxy for customer impact; the ops "team" is 2–3 generalists covering payments, cards, KYB and support (Loop-scale); the provided data is synthetic, so sending it to the OpenAI API raises no privacy concern.

## 5 · What I would improve with more time

- **With more time.** Swap the mock helpdesk for a production adapter — the two-method seam already exists, what remains is the unglamorous part (OAuth, webhooks instead of polling, rate limits, idempotent write-backs); auto-draft help-center articles to deflect the 53% repeat volume and measure actual deflection; wire the closure baseline check to post-fix ticket streams so `loop_closed` is fully automatic; extend the eval to draft quality with rubric-based grading; ship the console as a continuously-updated hosted view so non-technical stakeholders always see the live queue.
